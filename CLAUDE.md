## Project Overview
Casual multi-level turn-based artillery game. Drag-and-release trajectory combat to destroy the
opposing army and its structures. Modern military theme (inspired by Archery Bastions / Castle War).

**THIS REPO IS THE PRODUCT.** The Kotlin + SceneView/Filament build at

**Run `PortSelfTest.Run` after every change.** Its checks assert the behaviour the comments
describe, not that the code compiles — several of them exist because the thing they check silently

references. A code-only change does not need one; a new `[SerializeField]` does.

## Game data is authored HERE, in Unity (since 2026-08-06)

**The ScriptableObjects in `Assets/GameData/` ARE the source of truth.** Edit them directly. The
Kotlin export pipeline is retired; the old repo is reference only.

**Read `LEVEL_AUTHORING.md` before authoring or editing a level** — the six composition rules,
moved here from the Kotlin. They are checked, not merely documented:

```bash
DISPLAY=:1 $U -batchmode -quit -projectPath . -executeMethod LevelComposition.Report -logFile -
DISPLAY=:1 $U -batchmode -quit -projectPath . -executeMethod SandboxLevels.Generate -logFile -
```

`LevelComposition.Report` measures every campaign level by BUILDING it and reading the same
half-widths the camera uses, so it cannot disagree with the game. The same checks render live in
the level's inspector. Warnings are advisory — a level may bend a rule for a reason, and that
reason belongs in its `designNotes`. Errors are the locked 7–30 roster scale.

`SandboxLevels.Generate` rebuilds the eight roster/grouping rigs, which are the only GENERATED
levels. It used to run as a side effect of every import, which is why the level list came from two
places at once; it is a deliberate command now.

**`LegacyKotlinImport` still exists and will destroy your work.** It overwrites every asset in
`Assets/GameData` from `data.json`, in place, with no undo. It refuses to run without
`-iAcceptDataLoss`. Do not remove that guard.

## Rules that keep biting (full detail in HANDOVER.md)

**C# / Unity**
- Unity 6000.0 is **C# 9**. `record` works; `record class` does not. `init` needs the
  `IsExternalInit` shim.
- `GameState` uses **reference equality on purpose** — value equality on ~90 fields exceeds
  clang's bracket limit under IL2CPP and the Android build fails outright.
- **No `GameObject.CreatePrimitive` in RUNTIME code.** It attaches a Collider, IL2CPP strips
  collider classes, and the call takes the whole level build down on device. Use `QuadMesh`.
  Editor code is fine — nothing is stripped there, which is why this cannot show up until a
  device build.
- **`Mathf.SmoothStep` is a smoothed LERP between its first two arguments**, not GLSL's
  `smoothstep`. It has silently flattened a generated falloff twice.
- Anything shaped by **alpha must clone a TRANSPARENT material ASSET**. An opaque URP/Unlit
  ignores alpha entirely — the thing holds full strength and then vanishes in one frame.
- Pooled objects share a material: per-instance tinting needs a `MaterialPropertyBlock`.

**UI (uGUI + TextMeshPro, added 2026-08-06)**
- `BattleUI` builds its whole hierarchy IN CODE at runtime. No prefab and no serialized refs, so
  **a UI change never needs a scene rebuild**. Build from `Create()`, not `Awake` — Awake does not
  run in edit mode.
- **No character outside ASCII in a TMP string.** The default font asset is ASCII-only and renders
  `★` / `◆` as missing-glyph boxes, silently. Stars and the coin icon are drawn sprites.
- IMGUI draws AFTER a ScreenSpaceOverlay canvas, so anything IMGUI still draws sits on top of the
  UI and keeps eating its taps.

**Coordinates and rendering**
- `GameSpace.ToUnity` **negates X**. Route every placement through it — a mirrored scene looks
  entirely plausible.
- **The camera sits ~6° above the ground plane.** A decal lying flat is therefore seen nearly
  edge-on and its on-screen HEIGHT is its world depth times the sine of that angle — about a
  tenth. Size ground decals in DEPTH, never in width; width just makes a wider smear.
- Backdrop geometry is sized against the frustum AT ITS OWN DEPTH. Never read `Screen` in
  batchmode — it reports a placeholder desktop resolution.

**Pools and slots**
- Pools are built **ONCE** and survive a level switch. Minting a render slot mid-session is the
  failure the Filament build paid for repeatedly.
- What must be reset on a switch is everything that reads a slot's PREVIOUS occupant: pose,
  position, animation state, and any material the level tints.
- **Stopping an animation does not undo it.** Ask what each clip WRITES and make sure something
  restores every channel — `die` drives the ROOT and `idle` does not, so a recycled slot came back
  playing a breathing loop while lying on its back.

## Art — Blender → glTF

Builders live in the OLD repo's `tools/blender/`. Export `.glb`, apply all transforms, low-poly,
flat, vertex colours or small shared textures.

- **Colour binds to MESH NAMES by prefix**, animation binds to JOINT names by path, and neither
  knows about the other. Four tones, matched in order: `skin*` → shared flesh, `trim*` → per-class
  signature colour, `accent*` → dark gear, everything else → the side's uniform.
- **Units are built on a LIMB HIERARCHY** (`build_units_rigged.py`): `root → leg-left, leg-right,
  torso → (arm-left, arm-right, head)`. Three constraints bind and only these three — joint names
  and paths exact, model height ~2.70, and the soldier faces glTF **+Z** (so it is built facing
  Blender **-Y**). Kenney's CC0 clips drive it; joint POSITIONS are free.
- **Roster: 8 unit definitions, 7 models, 6 pickable.** Every survivor is distinct on a MECHANIC,
  not on stats.
- **Measure before authoring.** `python3 tools/measure_units.py` (band profile — legs/torso/head)
  and `tools/measure_structures.py` (silhouette fill/profile/roofline), both in the old repo.
  Judge the SPREAD ACROSS THE SET, never one class alone: hitting every individual target is what
  destroyed the spread once already.
- **Height is not an axis** — every unit normalises to the same on-screen height. Width is all
  there is, and it has to be spent on the axis the camera SEES.
- **Anything body-relative is sized against `UnitGeometry.UnitScaleUnits`** — parapets, packs,
  health bars, shadows. A prop authored against an older unit scale comes out wrong the day the
  unit changes, and that has happened to merlons, sandbags and an ammo drum.

## Levels

**Currently seven campaign levels** (Mountains, Forest, MountainsDusk, Winter, Desert, CityRuins,
Ocean) plus 17 test rigs — 24 total. **Heading for 12–18** under `PRODUCT_DIRECTION.md` Tier 0.1:
one level per biome was an ART constraint, never a content limit, so biomes REPEAT with different
jobs. Author against the beat chart in that file.

The six composition rules live in **`LEVEL_AUTHORING.md`** (moved out of the Kotlin 2026-08-06)
and are checked by `LevelComposition.Report`. Shortest form: the Aiming camera frames the
PLAYER LINE ONLY (~6 wide), scout/resolve framing is set by the enemy cluster INCLUDING structure
edges (under ~11), one dominant structure plus at most two small supports, 14-18 units of
separation TANK→DOMINANT STRUCTURE, and garrison the MAJORITY of the enemy roster on structures.

**Test levels must be renumbered whenever the campaign changes size** — the switcher indexes by
position, and `PortSelfTest` asserts `levelNumber == index + 1`.

**The 17 TEST RIGS are disposable instruments** — change them freely to exercise a mechanic. The
CAMPAIGN is no longer scrap: as of `PRODUCT_DIRECTION.md` it is the product's teaching funnel and
each level owes one beat.

## Debugging

- **The FREE CAMERA (CAM button) is the first tool to reach for.** It flies anywhere and HOLDS,
  through volleys and the victory screen, with a live x/y/z readout in GAME space. Half this
  project's visual bugs were confirmed in seconds once the camera could be parked in front of the
  thing. Drive it from adb with `input swipe X Y X Y 600` — a tap is too brief now that it is
  hold-to-fly.
- **`Auto` is a test harness, not the player.** Every unit targets its nearest enemy with no
  jitter, so it kills rather than wounds and cannot test structures at all. Measure difficulty,
  and anything that depends on spread, with real drags.
- **Prefer a PROBE to a detector.** A one-build `Debug.Log` at both ends of a suspect path settles
  in one run what a pixel-search will get wrong three times — this session alone, detectors locked
  onto HUD text, tracers, a boot and a bunker window, and twice declared a working feature broken.
- **A search that finds nothing is not evidence of absence** until it has been shown to find the
  thing when it IS there.
- `screencap` sometimes returns a black 15KB PNG with the screen on; pull a frame from
  `screenrecord` instead.

## Performance

- Target 60 fps; the panel is pinned to a steady 60. **Smoothness is bought with a rate that never
  changes, not with more frames** — measured against the reference game, which burns 3x the CPU
  and feels better because it holds one rate.
- Measure work in **instructions**, not CPU% (`simpleperf stat -e instructions`): threads migrate
  between 400MHz and 3.05GHz cores, so CPU% measures core placement as much as work.
- **Never measure performance on a development build.**
- Low draw calls and node count; shared materials; aggressive reuse.

## Conventions

- Immutable state + `with` updates; all game logic in `ArmedConflict.Game`, engine-independent.
- No gameplay logic in MonoBehaviours — `BattleRunner` renders and takes input, nothing else.
- `dt` VARIES. Never write a decay or lerp constant as a bare per-tick multiply; run it through
  `CosmeticSystems.DecayPerTick60` or a dt-parameterised primitive.
- Anything that decays must decay on EVERY tick path, including the one taken once the battle is
  over — a value that only decays in the combat block freezes forever on the victory screen.
- Stats live in Definition classes, never hardcoded.
- `var` where the type is obvious, explicit null handling, self-documenting code.
